# 设计说明

这份文档解释「记忆与成长」（包名/插件 ID `dsh-ref-develop`）为什么是这样，而不是记录 API。
API 见 README，数据格式见 `docs/MEMORY-FORMAT.md`。

## 目标与非目标

**目标**

1. 会话结束后，可复用的经验能被写成条目，下次会话开始时就出现在系统提示词里。
2. 每条经验都能追溯回原始对话（哪次会话、哪一回合、哪句话），而不是模型凭空生成的结论。
3. 使用者能选择全局共享或单工作区记忆，切换成本低。
4. 成长面覆盖日常：方法、教训、读书/新闻/论文知识、各学科题目复盘、项目状态。
5. 可选地学习「用户」的稳定偏好，且默认关闭。
6. 零运行时依赖，装不上包也不会失效；失败不打断会话。

**非目标**

- 不做通用 RAG：不建向量库、不索引全部历史会话。需要细节时由模型调用 `growth_recall`。
- 不做多人共享服务端：记忆落本机，不联网同步。
- 不替用户做决策：记忆是草稿，冲突时以当前事实为准。
- 不记录密码、令牌、私钥；提炼提示词明确要求脱敏，写入工具也不校验（这是使用者的责任）。

## 分层

```text
事件层    agent/created, agent/pre-step, agent/turn-stopping
          ↓
笔记层    sessions/<id>.md        每回合一行摘要，零模型成本
          ↓
提炼层    consolidate.js          每 N 回合用当前模型提炼 + 证据校验
          ↓
条目层    memory.jsonl           权威数据，JSONL 追加可审计
          ↓
视图层    MEMORY/*.md            给人看的视图，随时可重建
          ↓
注入层    prompt.js → systemPrompt.section
          recall.js 按本轮问题挑 top-k，受 promptBudgetChars 约束
```

把「笔记」和「条目」分开是有意的：笔记便宜、无损、失败也能留档；条目贵、有推断、
可能出错。两者都保留，出错时可以回看笔记重提炼。

## 关键决策

### 为什么不读历史会话全文

插件只在当前会话的事件流上工作，跨会话靠落盘条目传递。原因：读取全部历史会话
需要额外存储扫描与摘要成本，而且大部分历史与本轮无关。真正需要的「跨会话经验」
已经以条目形式存在磁盘上。

### 为什么默认用关键词打分，向量检索只作可选叠加

零依赖是硬约束，因此默认路径不引入向量检索：拉丁词 + 汉字 bigram 分词，标题权重最高（6）、标签（4）、
正文（2），叠加置信度/使用次数/新鲜度。可解释、可调试，命中率在日常使用中够用，
条目数量到几千条时仍是毫秒级。

关键词打分的短板是「换了说法就召不回」。向量检索正好补这一块，于是做成**可选的第二信号**而非替代品：
`embeddingProvider: none` 时 `semantic` 恒为 0，排序与纯词法版本逐值相同（有测试固定这一等价性）；
开启后 `score = lexical×(0.5+strength) + strength×0.4 + semantic×2.4×max(0.35,strength)`，
两项相加而非取其一——精确命中的术语不该被模糊语义挤掉。失败一律降级：嵌入请求报错只记 warn 并返回空列表，
那一轮退化为纯关键词，不打断会话。

### 为什么合并规则以标题为主

早期版本用标题+正文的加权相似度，结果把「关于 X 的结论」这种模板化正文的不同主题
合并成一条（12 条并发写入只剩 1–3 条）。现在标题相似度低于 0.5 直接判为不同条目，
高于 0.5 才加权正文；阈值默认 0.7。宁可多一条，不可丢一条。

### 为什么偏好要按切面取代

「用户喜欢中文」与「用户喜欢英文」如果按普通相似度合并，会得到一条自相矛盾的记忆。
因此 `preference` 用 `meta.aspect` 做键：同一切面出现新值 → 新条目取代旧条目
（旧条目 `status: superseded`、`supersededBy` 指向新条目），证据保留。

### 为什么要证据校验

模型提炼会编造具体命令和结论。`validateItems` 要求每条候选给出原文引用（quote），
把 quote 归一化后到会话转录里查找：找到 → `verified: true`；找不到 → `verified: false`
且置信度减半。没有直接丢弃，是因为转述式引用也可能合法；但降权后它会更快衰减。

### 为什么强度要衰减

记忆不清理会变成噪声。强度 = `confidence × 0.5^(age/halfLifeDays)`，加上
使用次数（每次 +0.02）与证据数（每条 +0.03）的加成。半衰期默认 30 天。
被 `growth_recall` 命中会 `touch` 更新时间，常用条目因此活得更久。
`preference` / `state` 不参与条数淘汰，但同样衰减——过时的画像不该一直生效。

### 为什么切换范围默认不迁移

三种范围（global / workspace / off）是**互相隔离的库**，不是同一份数据的视图。
切换只改变「读哪一份」，因此：

- 全局库不会被某个工作区的条目污染，工作区之间也互不可见；
- 关掉插件、选「无」、或会话目录不在所选工作区内时，会话回到默认状态：
  摘要为空串、不写会话笔记、不提炼，工具调用直接返回「记忆未启用」；
- 想搬数据时显式 `migrate=true`，只复制目标库没有的活跃条目（按 id 去重），
  源库保留；软删除 / 已取代的条目不迁移。

`workspacePaths` 是白名单：会话 cwd 必须等于其中一项或位于其下（`pathInside`，Windows 大小写不敏感）。
列表为空时视为未启用，会话保持默认状态。

### 为什么设置页走自建 HTTP 路由

Web 客户端只暴露 `layout/locale/sessions/slots/theme/timer/uiWorkspace/workspaces`，
没有通用宿主 RPC。因此 UI 注册到 `settings.section` 槽位，数据通过宿主
`webServer.register({kind:'prefix', path:'/growth-note/api'})` 提供，同源 fetch。
接口只接受 loopback Origin，请求体上限 256 KB。

### 为什么写文件要原子化 + 加锁

多个会话可能同时写同一个全局记忆库。`fsx.js` 用「同目录临时文件 + rename」保证
不会读到半个文件；`<file>.lock`（`wx` 打开，15 秒视为陈旧）把并发写串行化，
最多等 3 秒，超时后仍继续写（宁可偶发冲突，不阻塞会话）。

### 为什么向量索引与记忆数据分开存

`vectors.jsonl` 与 `memory.jsonl` 是同目录的两个文件，绝不是同一条记录的两半：

- 向量是**派生数据**，删掉只损失召回质量，不损失任何记忆事实；
- 换模型后旧向量全部过期（`sig` 字段记录 `provider:model`），重建即可；
- `memory.jsonl` 的格式与 schema 版本不因是否启用向量而改变，关闭向量功能不会改动任何条目。

代价是两份文件可能短暂不一致（条目已改、向量还没重算）。处理方式是「宁缺毋滥」：
条目一旦写入/合并/删除就**立即删除其向量**，宁可少一条向量等后台重算，也不让过期向量参与排序。
`#saveVectors` 同时清理磁盘与内存中指向已不存在条目的记录，避免 `vectorStats` 虚高。

### 跨会话 RAG 的接口契约（预留）

当前版本只在单一记忆库内做语义召回，但接口按「可替换嵌入 + 可替换候选集」设计，后续接跨会话检索时不需要改条目模型：

| 层 | 当前实现 | 扩展方式 |
| --- | --- | --- |
| 嵌入 | `createEmbedder(config)` → `{signature, available, embed(texts)}` | 新增提供者只需在 `EMBEDDING_PROVIDERS` 里加名字并实现 `embed`，或由外部注入 `fetchImpl` |
| 向量存储 | `store.loadVectors()/upsertVectors()/dropVectors()`，键为条目 id | 换成外部向量库时保持这三方法语义即可 |
| 召回 | `rankEntries({tokens, vectors, queryVector, embeddingWeight})` | 只要能把「若干候选条目 + 其向量」交给它，来源可以是别的库、别的机器 |
| 作用域 | 一次只查一个 `GrowthStore` | 多库检索 = 合并各库候选后统一 `rankEntries`，再按 id 回源取原文 |

已知尚未解决的问题：跨库合并时的强度可比性（不同库的 `halfLifeDays` 可能不同）、
证据引用跨库跳转（`evidence.sessionId` 属于别的会话日志）、以及增量同步时的向量漂移。
在解决这些问题之前，跨会话检索保持在「接口就绪、默认不启用」的状态。

## 事件选择

| 事件 | 用途 |
| --- | --- |
| `agent/created` | 注册该 agent 专属的提示词 section，预热记忆库 |
| `agent/pre-step` | 从本轮首条用户消息提取召回关键词，刷新摘要 |
| `agent/turn-stopping` | 回合收尾：写笔记；到达间隔时异步提炼（不阻塞回合） |

摘要同时注册了全局 section（无 agent 上下文时兜底）与 per-agent section
（闭包捕获 agent，`AssembleContext` 本身不带 agent 信息）。

## 失败模式

| 失败 | 行为 |
| --- | --- |
| 模型不可用 / 超时 | 只写会话笔记，`reason: 'no-model'`，不报错 |
| 模型输出不是 JSON | `extractJsonArray` 失败，保留笔记，`reason: 'bad-json'` |
| 引用找不到 | 条目仍写入，`verified: false`，置信度 ×0.5 |
| 磁盘写失败 | 记 warn 日志，会话继续；下次写入重试 |
| 锁等待超时 | 3 秒后放弃锁继续写，靠原子 rename 兜底 |
| 设置文件损坏 | 回落默认配置 |
| 记忆库不存在 | 首次使用时自动创建目录与空文件 |
| 嵌入服务不可用 / 密钥失效 | 只 warn 一次并返回空向量，当轮退化为关键词召回，不阻塞会话 |
| 向量与条目不同步 | 条目变更即删向量；后台按 `sig` 差异重算，最坏情况少召回几条 |
| 模型被更换 | 旧向量 `sig` 不匹配，自动视为过期并重建，不产生错误相似度 |

## 后续可做

- 记忆的「冲突检测」：新条目与旧状态矛盾时提示模型确认，而不是静默合并。
- 跨会话的 wp 聚类：同一题型的多次复盘合成「套路」。
- 按工作区标签过滤全局记忆（例如只在某类项目注入某些方法）。
- 摘要缓存持久化，减少重启后的首轮冷启动。
- 跨记忆库的合并检索（见上文「跨会话 RAG 的接口契约」中列出的三个待解问题）。
